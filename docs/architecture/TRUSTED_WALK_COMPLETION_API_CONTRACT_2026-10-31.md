# Trusted Walk Completion API Contract — 2026-10-31

Status: PROPOSED — contract only. Not implemented, not deployed, and not approved as a final production policy.

## 1. Purpose

Replace Partner-app direct writes that currently fail the checked-in Firestore Rules and must not be enabled by broad client write permissions. The backend is the authority for walk completion. Partner app submits an authenticated request; backend validates it and commits the result once.

## 2. API boundary

Proposed callable Cloud Function: `completeWalk`.

The callable must use Firebase Authentication context. It must not accept a caller-supplied walker UID as authority. Derive the actor UID from `request.auth.uid`.

Proposed request fields:
- `bookingId`: required parent booking ID.
- `occurrenceId`: required stable ID for the individual scheduled walk. This is a prerequisite; the current Customer writer creates parent bookings with nested schedules and does not yet create canonical occurrence documents.
- `walkId`: optional idempotency key only if generated by a documented client protocol; preferred backend behavior is deterministic mapping from occurrence ID to one stable walk ID.
- `handoverProof`: required structured proof reference/type, not raw OTP in logs.
- `completionLocation`: latitude, longitude, accuracy metres, client captured-at timestamp.
- `routeSummary`: optional bounded summary (distance/duration); never trust client values as the sole proof of completion.
- `clientRequestId`: optional retry correlation ID, not the canonical walk identity.

Do not accept client-supplied `walkerId`, payout amount, price, payment state, verification status, final booking status, or arbitrary Firestore field maps.

## 3. Server-side preconditions

Before writing, validate all of the following:
1. Authenticated caller exists.
2. Walker document exists and is eligible: approved, active, and canonical status is approved. Confirm exact field contract with KYC/backend owner before coding.
3. The occurrence exists, belongs to the supplied parent booking, and is assigned to caller UID.
4. Parent booking exists and its current state allows completion; enforce an explicit transition graph.
5. The occurrence is in a completable state and is not cancelled, expired, already reassigned, or already completed.
6. Safe handover is confirmed by a server-verifiable mechanism.
7. Completion location is syntactically valid, within coordinate bounds, has acceptable accuracy, and is consistent with the approved return policy. Distance thresholds and exceptions must come from an approved policy/config, not hard-coded guesses.
8. Any OTP or handover token is valid, unexpired, bound to this occurrence, and one-time consumable. Never read an OTP from the booking document in the Partner client.
9. Required timestamps and duration are valid. Server timestamps are authoritative; client timestamps are evidence only.

A GPS point alone does not prove that a dog was safely handed to the right recipient. GPS and handover verification must remain separate checks.

## 4. Transaction and idempotency

Within a Firestore transaction:
- Re-read walker, occurrence, parent booking, and handover-verification state.
- Re-check assignment and state transitions inside the transaction.
- Resolve one canonical walk ID for the occurrence. Prefer deterministic `walks/{occurrenceId}` or a stored `walkId` on occurrence; decide the final ID scheme before implementation.
- If already completed by the same valid completion, return the existing canonical result without creating a second walk record.
- If completed by another actor or inconsistent state, reject and create a security/audit signal through a trusted path.
- Create the walk record once.
- Mark occurrence completed and update the parent booking/summary fields only according to the agreed parent aggregation rules.
- Consume handover token/OTP atomically with completion.
- Write an immutable audit event with actor UID, occurrence ID, walk ID, event type, server timestamp, and request correlation ID.
- Ensure transaction retries cannot create duplicate payout/ledger entries. Payout ledger creation should be a separate idempotent verified event or a transactionally coupled outbox, not a client write.

Do not use random walk document IDs generated anew on every retry.

## 5. Proposed canonical walk record

`walks/{walkId}` fields (final schema to be aligned with Customer, Partner, Admin and Firebase owners):
- `walkId`, `bookingId`, `occurrenceId`
- `walkerId` (derived from auth UID)
- `customerId` (copied from trusted booking/occurrence)
- `status: completed`
- `startedAt`, `completedAt` (server timestamps / trusted server-derived values)
- `durationActualSeconds` (validated server-derived or bounded evidence)
- `distanceMeters` (validated evidence, clearly marked source)
- `handoverVerification`: method, verifiedAt, verifier/result reference; never store raw OTP
- `completionLocation`: coordinates, accuracy, capturedAt, serverReceivedAt
- `createdAt`, `updatedAt`

Do not copy full KYC documents, raw OTP, or unnecessary customer personal data into the walk record.

## 6. Error contract

Return stable machine-readable codes:
- `unauthenticated`
- `walker_not_eligible`
- `occurrence_not_found`
- `booking_occurrence_mismatch`
- `not_assigned_to_caller`
- `invalid_state_transition`
- `handover_not_verified`
- `handover_token_expired`
- `completion_location_invalid`
- `completion_conflict`
- `already_completed` (include existing canonical walk ID/result where safe)
- `internal`

Partner UI must show a retry-safe state for network/internal errors. It must not locally display a completed walk until the backend confirms completion or returns the existing completed result.

## 7. Security and privacy

- Callable validates Firebase Auth and all ownership/assignment server-side.
- App Check should be enforced when platform readiness permits; it is an additional control, not a replacement for Auth/authorization.
- Rate-limit OTP verification attempts and completion retries.
- Do not log OTPs, KYC values, full addresses, or raw sensitive payloads.
- Keep location precision and retention limited to the approved operational/legal requirement.
- Client Firestore writes to privileged completion fields remain denied.
- Add explicit Rules for authorized read access to walk history only after data ownership and field exposure are reviewed.

## 8. Required Emulator test matrix

1. Unauthenticated caller rejected.
2. Walker not approved rejected.
3. Inactive walker rejected.
4. Wrong walker/assignment rejected.
5. Missing occurrence rejected.
6. Parent booking mismatch rejected.
7. Cancelled/reassigned/expired occurrence rejected.
8. Invalid state transition rejected.
9. Missing handover proof rejected.
10. Expired OTP/token rejected.
11. Reused OTP/token rejected.
12. Invalid/out-of-range/poor-accuracy location rejected.
13. Completion within policy accepted.
14. Retry with same occurrence returns same walk ID and creates no duplicate.
15. Concurrent completion requests produce exactly one canonical walk.
16. Transaction failure leaves no partial completion.
17. Client cannot write walk record or privileged booking completion fields directly.
18. Audit event exists exactly once for successful completion and contains no secret.
19. Parent booking aggregate remains correct for multi-walk bookings.
20. A completed occurrence cannot be reassigned or completed again.

## 9. Dependencies / decisions before implementation

Blocking dependencies:
- Define canonical `walk_occurrences` collection and stable occurrence IDs. Current Customer booking writer stores nested schedule arrays in parent booking.
- Define the state machine and parent-booking aggregation for multi-day / multiple-walk bookings.
- Approve safe handover verification mechanism and OTP lifecycle.
- Approve return-location threshold and exception path.
- Define trusted start-walk and GPS ingestion contracts; completion must not infer a valid start from client state.
- Agree read model for Partner, Customer and Admin.
- Confirm whether payout ledger is triggered by verified completion or by a later review/settlement step.

## 10. Implementation sequence

1. Cross-app owners approve occurrence and completion schemas.
2. Add Functions implementation with transaction and typed validation.
3. Add Functions Emulator tests from section 8.
4. Add Rules tests proving direct client completion writes remain denied.
5. Integrate Partner app with callable and retry-safe UI.
6. Integrate Customer/Admin read models.
7. Run all repository CI and cross-app integration tests.
8. Review production Rules/Functions diff and obtain explicit deployment approval.
